# Qwen3.8-Flash-Next: CUDA graphs (FULL_DECODE_ONLY) without torch.compile

**Date:** 2026-08-28
**Profile:** `qwen3.8-flash-next-aixiaoma` (TP4, EP, MTP4, W4A16 MoE, bf16 KV, max_model_len=155000)
**Change:** `--compilation-config '{"mode":0,"cudagraph_mode":"FULL_DECODE_ONLY"}'` (mode stays 0/eager — no torch.compile), `VLLM_GPU_MEM_UTIL` 0.95 -> 0.97.

## Background

Investigated whether full `torch.compile` (`mode:3` / `VLLM_COMPILE`) could be
made to work on this hybrid GDN (qwen4_exp) architecture, since it crashes
today with a dynamo shape-specialization error. Traced the crash to
`vllm/models/qwen4_exp/amd/ple_layer.py`'s
`if input_ids.shape[0] != hidden_states.shape[0]: raise ValueError(...)` —
a Python `!=` comparison between two independently-dynamic tensor sizes that
torch.compile's guard system can't resolve under `dynamic_shapes_config:
unbacked` (`Could not guard on data-dependent expression Ne(u1, u0)`).
Replacing the raise with `torch._check(a == b, ...)` eliminated that crash.

However, once past the guard crash, compile mode hit a **hard CUDA OOM
during Inductor's compile/autotune pass itself** — proven independent of
context length, cudagraph settings, and KV-cache utilization by three
isolating tests:

1. Shrinking `max_model_len` 155000 -> 16384: same OOM, same ~31.25 GiB
   allocated per GPU.
2. Restricting `cudagraph_capture_sizes` to `[1,2]`: same OOM.
3. Disabling cudagraph capture entirely (`cudagraph_mode: NONE`, compile
   still mode 3): same OOM.
4. Dropping `gpu_memory_utilization` 0.95 -> 0.80 -> 0.55: **identical
   "free: 110 MiB" byte-for-byte across all three**, proving the OOM
   happens *before* the KV-cache memory budget is even applied — Inductor's
   compile-time scratch memory need exceeds available headroom on a 68 GiB
   model at TP4 on 32 GiB GPUs, regardless of tuning.

**Conclusion: full torch.compile is not practically feasible on this
model/hardware combination** without upstream changes to reduce
compile-time memory overhead. The `torch._check` fix is a genuine, useful
bug fix for anyone attempting compile on qwen4_exp, but was not committed
here since it can't be validated as delivering value without the OOM being
solved first.

## The actual win: CUDA graphs don't need torch.compile

CUDA graph capture in vLLM is independent of torch.compile — `cudagraph_mode`
can be set without `mode:3`. Testing `mode:0` (eager, no compile) +
`cudagraph_mode: FULL_DECODE_ONLY` avoided the Inductor OOM entirely (no
compile pass to OOM in) while still capturing prefill+decode CUDA graphs,
eliminating most of the per-op kernel-launch dispatch overhead that
eager-mode execution pays on every decode step for this hybrid GDN
architecture's many small per-layer ops.

First attempt at `gpu_memory_utilization=0.95` (unchanged) failed with a
**graceful `ValueError`, not a crash**:

```
ValueError: To serve at least one request with the model's max seq len
(155000), (2.31 GiB KV cache is needed, which is larger than the available
KV cache memory (1.93 GiB). ... estimated maximum model length is 125664.
```

Bumping `gpu_memory_utilization` to 0.97 (cudagraph capture buffers need a
small amount of extra headroom beyond the eager-mode budget) restored full
155000 context and booted cleanly.

## Stability / coherence validation

- 5x short chat-completion requests: all coherent (counting 1-10 correctly
  each time).
- 1x long generation (max_tokens=1200): completed without crash or OOM
  (model spent all 1200 tokens on `reasoning` content — a model behavior
  unrelated to this change — but decode ran the full length cleanly,
  confirming stability over many decode steps).
- No `OutOfMemoryError`/`OOM`/error log lines during the full soak (~15 min
  of testing across multiple boots and requests).
- Container stayed `healthy` throughout; no crash-loop.

## Conclusion

Adopted as the new production default for
`env/qwen3.8-flash-next-aixiaoma.env`: `VLLM_GPU_MEM_UTIL=0.97`,
`VLLM_EXTRA_ARGS` compilation-config updated to include
`"cudagraph_mode":"FULL_DECODE_ONLY"`. This is a pure config change (no
source patch), carries no torch.compile/Inductor risk, and delivers the
single largest tok/s win found so far on this profile.
