Fresh numbers on the stock build (vLLM v0.28.0rc2, torch 2.13, AITER v0.1.20,
`ROCM_AITER_UNIFIED_ATTN`, TP=2, 128K max-model-len,
`--gpu-memory-utilization 0.92`, `--max-num-seqs 2`,
`--max-num-batched-tokens 4096`), bf16 KV (`VLLM_KV_CACHE_DTYPE=bfloat16`).

**MTP4 re-enabled** in this run: `env/qwen3.6-35b-a3b.env` had MTP disabled
(`VLLM_SPEC_DECODE=`) since the `#47087` Qwen3-MoE MTP token-loop bug. The
upstream fix (`#51113`) landed in v0.27.1, so this run re-tests MTP4 on the
v0.28.0rc2 build. `SpeculativeConfig(method='mtp', num_spec_tokens=4)` confirmed
in engine logs. Method: `llama-benchy 0.4.0`, `--pp 2048 --tg 32 128 --runs 3`,
thinking off, single request. Coherence **PASSED**, plus a manual 512-token
long generation was fully coherent with varied, quantitative output (no
degenerate repetition).

## Verdict: MTP4 is safe on Qwen3-MoE in v0.28.0rc2

The `#47087` token-loop bug did **not** recur. Coherence test passed and a
manual 512-token generation stayed coherent and varied. MTP4 delivers a
**~2x decode win** on the MoE model (tg32 194.9 vs 87.8, tg128 161.3 vs 87.1).
pp2048/TTFT is slower (~-35%), consistent with the dense 27B trend on the
current build + bf16 KV; pp2048 variance is large (run 2 ±2154 t/s) under the
4096 `max_num_scheduled_tokens` spec-decode scheduling. See the AGENTS.md
`#47087` watchlist note for the updated "pending re-test" status.

The env override was dropped (`env/qwen3.6-35b-a3b.env`), so MTP4 is now
inherited from `env/qwen3.6.env.common` — 35B-A3B ships MTP4 by default.
