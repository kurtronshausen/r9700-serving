# vllm-radiance TP=2 bring-up: Qwen3.8-27B-FP8 baseline

Date: 2026-08-30. Prebuilt `docker.io/stilldeadcode/vllm-radiance:0.9.3` image
(vLLM 0.27.1, ROCm 7.14, gfx1201-specific `libr4d` kernels), served from the
existing `/srv/llm/Qwen/Qwen3.8-27B-FP8` checkpoint. TP=2 (GPUs 0,1), bf16 KV,
`--attention-backend=R4D`, `--mamba-cache-mode=align` + prefix caching, MTP
self-speculation (`num_speculative_tokens=8`) with `RADIANCE_DYNAMIC_DRAFT=1`,
vision enabled (`--limit-mm-per-prompt image:1`, matching the main `vllm`
service's `#40707` workaround), `--max-model-len=200000`.

## Boot validation

- 2x AMD Radeon AI PRO R9700 (gfx1201) detected, P2P access ENABLED 0<->1.
- R4D kernel selection: **17 of 17 queries resolved** (attention, GDN
  prefill/decode, all-reduce, skinny GEMM all engaged — none fell back to a
  generic path).
- `GPU KV cache size: 204,428 tokens` (1.02x concurrency at 200,000 max model
  len — tight but expected at `--max-num-seqs=8`/bf16 KV defaults; not yet
  re-derived per radiance's own `--kv-cache-memory` pinning recipe).
- No missing dense fp8_configs warnings at TP=2 — the image ships tuned
  configs for this exact model+GPU+TP shape already.
- Coherence: single-request arithmetic (chat + completions), 2 concurrent
  requests, and a vision (image input) smoke test all passed without error.

## Two bugs found + fixed during bring-up (not perf-related, config-only)

1. `--kv-cache-dtype=bf16` is not a valid vLLM 0.27.1 choice (`bfloat16`
   is) — this had been silently crash-looping the container
   (`RestartCount: 8`) since the service was first added to `compose.yaml`;
   it had never actually booted before this session. Fixed (commit
   `770313d`).
2. `--language-model-only` (upstream's suggested default for text-only
   serving of this VL checkpoint) was replaced with vision enabled +
   `--limit-mm-per-prompt='{"image":1,"audio":0,"video":0}'`, to match the
   main `vllm` service's own convention for this same model (commit
   `7580ecc`).

## Benchmark (llama-benchy 0.4.0, pp2048 + tg32/128, 3 runs, prefix caching on)

| test | t/s | peak t/s |
|---|---|---|
| pp2048 (run 1) | 3985.74 ± 1.49 | |
| tg32 | 81.49 ± 7.20 | 84.12 ± 7.44 |
| pp2048 (run 2) | 3055.90 ± 1325.18 (high variance — cold-cache JIT interference, first boot) | |
| tg128 | 89.64 ± 14.84 | 95.33 ± 9.46 |

For context, the same model on the main `vllm` service (TP=4, AITER unified
attention, fp8 KV) previously benched around pp2048 ~2400 t/s. Radiance's
R4D attention backend nearly **doubles prefill throughput** at TP=2 vs the
main stack's TP=4 AITER path — consistent with upstream's documented
"+14.6% prefill at 64K" R4D win layered on top of TP=2's inherently lower
communication overhead vs TP=4. Decode (tg32/tg128) is in the same ballpark
as flashnext's best numbers (~82-90 t/s), on a completely different model.

## Known limitations / not yet done

- Context capped at 200,000 (not yet re-derived for max headroom).
- `--kv-cache-memory` not yet explicitly pinned (radiance's own 5-step
  recipe) — using auto-derived KV budget from `--gpu-memory-utilization`.
- TP=4 stretch goal not yet attempted (see `plan.md`) — `RADIANCE_USE_R4D_AR`
  (custom P2P all-reduce) is documented as tested only at TP=2.
- Vision was smoke-tested with a synthetic 1x1 PNG only (pipeline
  correctness, not output quality) — no real-world VLM eval done.
