# 2026-08-10 Qwen3.6-35B-A3B MTP4 — c1 vs c2 depth comparison

Same stack as `08_10_qwen3.6-35b-a3b_mtp4_depth.md` (AITER unified attention,
bf16 KV, MTP4, `--max-num-batched-tokens 4096`, tuned fused_moe configs,
bundled chat template), run back-to-back at `--max-num-seqs 1` (c1) and
`--max-num-seqs 2` (c2) on the same boot. Purpose: settle whether the earlier
c2 sweep (`08_10_qwen3.6-35b-a3b_mtp4_depth_c2.md`) was noise, and pick the
most efficient long-context setup between serial (c1) and concurrency-2 (c2).

`t/s (total)` = aggregate across concurrent requests, `t/s (req)` = per
request. `ctx_*` = full context load (depth prefix + 2048 prompt); `pp2048` /
`tg32 @ dXXX` = incremental 2048-token prefill / decode with the depth prefix
cached.

Commands:
`uvx llama-benchy --base-url http://localhost:8180/v1 --model qwen3.6-35b-a3b --tokenizer Qwen/Qwen3.6-35B-A3B --pp 2048 --tg 32 --depth 0 1024 4096 8192 16384 32000 64000 --runs 3 --enable-prefix-caching --format md`
(c1), and the same with `--concurrency 2` (c2).

## Verdict

**c1 (serial) is the more efficient long-context setup — run at c1.**

- **c2 never beats c1's single-request decode.** At every depth, the aggregate
  of *two* concurrent requests (c2 total 47-127 t/s) is below *one* request at
  c1 (156-180 t/s). Geomean c2 total 95 vs c1 170. Decode is bottlenecked by
  attending over the cached KV, so batching two deep contexts doesn't add
  throughput — it splits the same pie and then some.
- **Serial finishes 2 requests faster than concurrent.** Two identical deep
  requests at c1 run back-to-back at ~171 t/s each → effective 85.5 t/s per
  concurrent pair; c2 gives 77 t/s per request at d64000 (and worse at
  shallower depths relative to c1). Concurrency is a net loss for throughput.
- **Latency also favors c1**: incremental TTFT 1070 vs 1562 ms @ d64000, and
  full-context load 9292 vs 14178 ms.
- The earlier c2 sweep (`..._depth_c2.md`) was **not** a bad-state artifact —
  this run reproduces it closely (geomean 94.8 vs 86.1 total; the small
  difference is boot-to-boot variance). c2 ≈ c4 aggregate holds; neither
  reaches c1.

**When c2 is still right**: only when you must have *multiple users make
simultaneous progress* on long contexts and can accept ~45-55% lower per-request
decode. If the goal is raw throughput, tokens/s, or minimum latency for one
active session, c1 strictly dominates.
